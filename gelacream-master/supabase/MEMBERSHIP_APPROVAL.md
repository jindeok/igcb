# 웹앱에서 회원 가입 승인

## 이용 흐름

1. 새 사용자가 회원가입하고 기존 Supabase 인증메일로 본인 이메일을 인증한다.
2. 인증을 마친 사용자는 `승인 대기` 화면에서 기다린다. 승인 전에는 DB 레시피를 조회할 수 없다.
3. 관리자가 기존 웹앱에 로그인하여 메인 화면의 **회원 가입 승인 · 대기 N건**을 누른다.
4. `/admin/members`에서 이름·이메일·신청일을 확인하고 승인 또는 거절한다.
5. 관리자 한 명이 승인하면 이용 가능하다. 대기 화면은 15초마다 상태를 확인하며 승인 시 자동으로 메인 화면으로 이동한다.

관리자 알림메일과 가입 승인 완료 메일은 보내지 않는다. 별도 메일 서비스, 발신 도메인,
Gmail 앱 비밀번호, 서버 전용 Supabase 키, Netlify 예약 함수가 필요하지 않다.
관리자는 웹앱에 접속하여 대기 건수를 확인한다. 메인 화면과 승인 목록은 30초마다 갱신된다.
기존 가입 이메일 인증 및 비밀번호 재설정 메일은 Supabase Auth에서 처리한다.

## 권한과 기존 회원

- 최초 마이그레이션 시 존재하는 프로필은 `approved`로 유지한다. 역할 변경이나 재승인은 없다.
- 프로필을 삭제하여 사용 중지한 계정은 복구하지 않는다.
- 새 계정은 `staff/pending`이며, 이메일 인증을 마친 계정만 관리자 목록에 나타난다.
- 기존의 승인된 관리자 3개 계정이 처리할 수 있다. 가입 승인은 일반 회원 이용 허용이며 관리자 승격과 별개다.
- 조건부 UPDATE로 먼저 확정한 관리자 한 명의 결정만 반영한다. 처리자와 시간을 기록한다.
- 일반 사용자는 승인 목록을 조회하거나 자신을 승인할 수 없다. 프로필의 권한 및 승인 상태를 직접 수정할 수도 없다.
- DB RLS에서 승인 상태를 확인하므로 직접 API 호출에도 동일한 제한이 적용된다.
- 프런트엔드에 포함하던 샘플 레시피 폴백도 제거하여 조회 오류 시 데이터가 우회 표시되지 않는다.

## 배포

1. `npm ci`, `npm test`, `npm run typecheck`, `npm run build:web`.
2. SQL 마이그레이션을 파일명 순서대로 적용한다. `20261118000000_membership_approval.sql`은 최초 도입 기록이며, 최종 수동 승인 구성은 `20261118010000_manual_approval_only.sql`이다. 두 파일을 재실행해도 기존 승인·거절 결과는 유지된다.
3. `supabase/verify_membership_rollback.sql`로 운영 DB를 검증할 수 있다. 테스트 계정·승인 내역은 트랜잭션에서 롤백하며 실제 회원을 바꾸지 않는다.
4. Netlify는 `jindeok/igcb`의 `main` 푸시를 자동 배포한다. base는 `gelacream-master`, build는 `npm run build:web`, publish는 `dist`.
5. 최초에는 DB 마이그레이션을 먼저 적용하고 새 앱을 배포한다. 앱이 `approval_status` 컬럼을 사용하기 때문이다.

메일 도입 중 추가했던 서버 환경변수와 예약 함수는 최종 구성에서 제거한다.
기존 `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` 공개 설정을 사용한다.

## 보호 범위

가입 승인은 DB 레시피와 앱 화면에 적용된다. 기존 공개 이미지 버킷과 정적 이미지 URL은 이 변경으로 비공개 전환하지 않는다.
